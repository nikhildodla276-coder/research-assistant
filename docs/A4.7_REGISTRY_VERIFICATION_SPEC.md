# Phase A4.7 — Registry Capability Verification & Archival Specification

## 1. System Boundary and Architectural Scope

Phase A4.7 establishes the deterministic, machine-readable bridge between empirical development-time benchmarking (`CandidateCapabilityProfile`) and registry capability metadata (`CapabilityVerificationRecord` and `RegistrySnapshot`).

### Strict Non-Negotiable Invariants
- **ZERO Runtime Routing:** A4.7 implements no runtime routing, failover, or model arbitrator.
- **ZERO Multi-Provider Execution for User Queries:** Models are evaluated concurrently ONLY during offline development-time benchmarking. At runtime, only one qualified tool/model is selected.
- **ZERO Subjective Ranking:** No composite scores, leaderboards, or "best model" tags.
- **100% Deterministic Policy:** Zero arbitrary percentage thresholds. Contract satisfaction is strictly empirical and verifiable.
- **Zero Secrets / Zero Network Calls:** Registry structures contain zero credentials and operate strictly offline.

## 3. Registry Verification Schema

The empirical verification state of any candidate component is structured through `CapabilityVerificationRecord`:

- `candidate_id`: Unique canonical candidate identifier (e.g. `groq_llama33_70b`).
- `candidate_type`: Classification (`INFERENCE_MODEL`, `RETRIEVAL_TOOL`, `EXTRACTION_TOOL`, `LOCAL_UTILITY`).
- `capability`: Target system functional capability (e.g. `structured_json_generation`, `claim_identification`).
- `verification_status`: Deterministic outcome enum:
  - `UNVERIFIED`: No empirical task observations exist.
  - `VERIFIED_PASS`: 100% of evaluated benchmark tasks satisfied output contracts with zero execution failures.
  - `VERIFIED_FAIL`: Evaluated benchmark tasks violated output contracts or failed execution.
  - `BLOCKED`: Candidate execution was blocked by pre-probe safety, billing, or approval gates.
  - `NOT_READY`: Infrastructure or adapter is unsupported or misconfigured.
- `benchmark_id` / `benchmark_version`: Provenance tracking the benchmark suite evaluated.
- `observed_task_ids`, `passed_task_ids`, `failed_task_ids`, `blocked_task_ids`: Explicit task-level accounting.
- `evidence_ids`: Direct foreign-key references to underlying `BenchmarkEvidenceRecord` items.
- `contract_satisfied_count` & `contract_satisfaction_rate`: Quantitative contract metrics.
- `latency_statistics`: Non-subjective execution latency stats (`min_ms`, `max_ms`, `mean_ms`, `median_ms`).
- `provenance_state`: Source verification standing (`RETRIEVED_BY_SYSTEM`, `MODEL_CLAIM_ONLY`, `NOT_AVAILABLE`).

---

## 4. Deterministic Verification Policy (`POLICY_VERSION = "1.0.0"`)

1. **Contract-Based Verification:**
   A capability receives `VERIFIED_PASS` if and only if all evaluated tasks for that capability succeeded without error and satisfied 100% of their structural output contracts (`contract_satisfied == True`).
2. **Partial Evidence Handling:**
   If a candidate evaluates multiple tasks for a capability, and some pass while others are blocked or fail, the capability is **NOT** verified. The registry preserves the exact task boundaries (`passed_task_ids`, `blocked_task_ids`) and sets the status to `BLOCKED` or `VERIFIED_FAIL`.
3. **Unearned Trust Prohibition:**
   Capabilities declared in candidate manifests that lack empirical benchmark evidence remain `UNVERIFIED`. Manifest claims never automatically grant `VERIFIED_PASS`.
4. **Provenance Invariant:**
   Model-asserted citations remain `MODEL_CLAIM_ONLY`. They never increment system retrieval metrics unless verified by active retrieval tools.

---

## 5. Snapshot Archival

Snapshots (`RegistrySnapshot`) capture the state of all evaluated candidates against a benchmark suite. They are serialized as immutable JSON artifacts without database dependencies, providing an auditable historical record of system capabilities across benchmark versions.
